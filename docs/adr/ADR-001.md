# ADR-001 — Rebuild sur stack NestJS + PostgreSQL + monorepo

## Statut

**Accepted** — 17/09/2026

## Contexte

Le projet « Site.mg » (SaaS de création de sites web) existe en version 1 : une application Next.js fullstack (API routes Next + Prisma + MySQL + Bootstrap) fonctionnelle pour le noyau (auth avec vérification email, gestion de sites, builder visuel, publication par slug).

Le produit doit évoluer vers une architecture d'équipe professionnelle : backend dédié, plusieurs agents travaillant en parallèle, tests systématiques, scalabilité des fonctionnalités futures (Stripe, analytics, temps réel).

Décision utilisateur (17/09/2026) :
1. Stack cible : **NestJS + PostgreSQL** (backend séparé), frontend Next.js conservé.
2. **Reconstruction from zéro** de la base de code, organisée selon la gouvernance [AGENTS.md](../../AGENTS.md).
3. La v1 existante reste dans le dépôt comme **référence de spécification** pendant la reconstruction (aucune suppression sans décision explicite).

## Décision

* **Backend** : NestJS (Node.js), architecture modulaire (controller → service → repository), validation DTO.
* **Base de données** : PostgreSQL, migrations versionnées.
* **Frontend** : Next.js + React + TypeScript + React Query + Axios + Formik + Yup, consommant l'API REST du backend. Le framework CSS (initialement Bootstrap) a été remplacé par Tailwind CSS — voir [ADR-003](ADR-003.md).
* **Cache / temps réel** : Redis (sessions, rate limiting, WebSocket gateway plus tard).
* **Organisation du code** : monorepo (voir [ADR-002](ADR-002.md)).

## Alternatives considérées

| Option | Raison du rejet |
|---|---|
| Conserver la v1 Next.js fullstack | Ne sépare pas frontend/backend ; difficile de faire travailler deux agents en parallèle sans friction ; pas de modules/DTO/guards structurés côté serveur |
| Express/Fastify nu | Pas de structure imposée : chaque agent réinventerait ses conventions |
| Supprimer immédiatement la v1 | Perte de la spécification fonctionnelle qui sert de référence au Product Owner et à la QA pendant la reconstruction |

## Conséquences

* Positives : séparation claire des responsabilités, deux équipes (frontend/backend) peuvent travailler en parallèle autour de contrats d'API, NestJS impose une structure homogène, PostgreSQL plus riche (énumérations, JSONB, index partiels).
* Négatives / coûts : effort de reconstruction du noyau existant (auth, sites, builder, publication) ; deux processus à déployer ; contrats d'API à maintenir.
* Mitigations : le backlog Scrum ([docs/backlog/](../backlog/)) porte les user stories reconstruites une par une avec la Definition of Done ; la v1 sert de référence fonctionnelle tant que la parité n'est pas atteinte.
